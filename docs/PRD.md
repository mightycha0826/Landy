## 1. 제품 정의

**Landy는 충남삼성고 학생이 학교 계정으로 들어와, 신원을 먼저 밝히지 않고 새로운 사람과 대화하거나 특정 학생에게 익명편지를 보내는 교내 모바일 PWA다.**

두 가지 핵심 경험을 제공한다. 랜덤채팅은 짧은 대화로 시작해 양쪽이 동의할 때만 시간을 연장하고 정보를 단계적으로 공개한다. 익명편지는 받는 학생을 이름으로 찾되 발신자의 신원을 수신자에게 숨기는 비동기 대화다. 프로필·매너 온도·업적·교복 뱃지는 이 경험을 보조하며, 신고·차단·운영자 처리는 서비스의 필수 안전 장치다.

제품의 익명성은 **다른 학생에 대한 신원 비공개**다. 권한 있는 운영자는 안전 운영을 위해 신원과 내용을 열람할 수 있으며 해당 접근은 기록되어야 한다. 학교 명단, 학교 이메일과 학번을 전혀 처리하지 않는 서비스로 설명하지 않는다. 편지 검색에서는 수신 대상의 이름·학년·학번이 보인다.

### 해결하려는 문제 — 검증할 가설

| 사용자 문제 가설 | 제품 대응 | 검증할 질문 |
|---|---|---|
| 같은 학교여도 기존 친구 관계 밖의 사람에게 먼저 말을 걸기 어렵다 | 학교 안 랜덤 매칭, 익명 이름, 첫마디 도우미 | 첫 대화 시작의 부담이 실제로 줄어드는가? |
| 대화가 불편해질 때 관계를 끊거나 거절하기 어렵다 | 짧은 시작, 쌍방 연장, 나가기·차단·신고 | 거절/종료를 이해하고 안심해서 사용하는가? |
| 특정 학생에게 하고 싶은 말을 실명으로 바로 보내기 어렵다 | 수신자 이름 검색, 발신자 익명편지 | 익명편지가 유용한 대화를 만들고 괴롭힘을 늘리지 않는가? |
| 익명 앱의 정체·안전·운영 방식이 불명확하면 신뢰하기 어렵다 | 학교 인증, 역할별 운영, 신고 증거와 감사 기록 | 사용자가 익명성의 범위와 운영자 접근을 이해하는가? |
| 매칭 상대가 없으면 첫 경험이 끝난다 | 대기 상태 안내, 선택적으로 활성화되는 AI 봇 | 봇이 사람 매칭을 방해하지 않고 대기를 돕는가? |

### 목표와 비목표

**목표**

1. 설치·학교 인증·온보딩 후 첫 유효 대화까지의 경로를 이해하기 쉽게 만든다.
2. 학생 간 신원을 불필요하게 드러내지 않으면서, 서로 동의한 대화만 이어간다.
3. 불편한 접촉을 차단하고 신고·문의의 결과를 본인에게 전달한다.
4. 모바일의 입력·뒤로가기·알림 복귀·오프라인 상황에서도 글과 상태를 보존한다.
5. 운영자가 권한과 기록에 근거해 서비스를 통제하고 문제를 처리할 수 있게 한다.

**현재 범위 밖**

- 외부 학교·일반 공개 가입, 교사 대상 학생 앱, 공개 실명 SNS.
- 공개 편지 게시판·공개 댓글 피드. 과거 기능은 제거되었으며 현행 제품으로 적지 않는다.
- 그룹 채팅, 음성/영상 통화, 채팅의 자유로운 파일 첨부, 결제·광고·구독.
- AI 상담·정신건강 지원·운영자 대체. 봇은 표시된 대화 상대 기능이다.
- 관리자도 신원을 알 수 없는 완전 익명성, 학교 명단/성별의 독립적인 신원 인증 보증.
- 학생이 직접 완료하는 셀프서비스 계정 삭제. 삭제 요청은 운영 문의에 연결하고 `admin` 역할이 요청자·범위를 확인해 실제 삭제한다.

## 2. 사용자와 권한

### 주요 사용자 유형

아래 유형은 코드에서 확인한 기능 사용자를 설명한 것으로 인터뷰로 검증한 페르소나는 아니다.

| 사용자 | 주요 과업 | 필요한 경험 |
|---|---|---|
| 첫 방문 학생 | 설치, 학교 이메일 인증, 이름 확인, 비밀번호·성별·선호 설정 | 단계를 이해하고 실패 후 재시도할 수 있음 |
| 대화를 찾는 학생 | 새 상대 찾기, 쌍방 대화·연장·종료 | 현재 상태와 동의 규칙이 명확함 |
| 편지를 쓰는 학생 | 수신자 선택, 서식/서명 작성, 전송 | 다른 동명이인에게 잘못 보내지 않고 글을 잃지 않음 |
| 편지를 받는 학생 | 새 편지 열기, 답장, 보관, 원치 않는 편지 거절 | 발신자 추론 없이 안전하게 수신을 통제함 |
| 활동을 표현하는 학생 | 소개/관심사, 업적, 대표 뱃지, CNSA 인증 신청 | 어떤 정보가 누구에게 보이는지 이해함 |
| 운영 담당자 | 신고 검토, 제재, 문의 답변 | 필요한 권한·증거·기록을 갖추고 처리함 |
| 개발/관리 담당자 | 서비스 설정, 점검, 신원 열람, 운영진 권한 관리 | 변경 영향과 접근 책임을 확인함 |

### 운영 역할 — 초기 권한과 변경 가능성

운영 화면은 학생 PWA 설치 게이트와 별도로 `/admin`에서 시작한다. 권한은 역할명만이 아니라 서버가 가져오는 권한 목록과 DB 권한표를 따른다. 최고 관리자는 moderator/developer/beta 역할의 권한을 바꿀 수 있으므로 아래는 **초기값**이며 운영 상태의 확정값이 아니다.

| 역할 | 초기 권한 | 별도 제약 |
|---|---|---|
| moderator · 운영자 | 실시간 현황, 신고/사용자/제재, 서비스 열고 닫기, 문의, 감사 기록 | 기본 신원 열람 없음. 기간 정지는 최대 7일, 영구 정지는 admin 역할만 |
| developer · 개발자 | 실시간 현황, 운영 설정, 서비스 열고 닫기, 문의, 감사 기록 | 기본 신고 처리·신원 열람 없음 |
| beta · 베타테스터 | 실시간 현황 | 기본 쓰기 운영 권한 없음 |
| admin · 관리자 | 모든 제품 운영 권한 | 신원 열람/대화 export는 기록 필요. UI의 기간 정지 상한은 365일 |
| owner · 최고 관리자 | admin 중 운영진 관리 속성을 가진 계정 | 역할과 별개인 속성. 운영진 지정/해제·역할별 권한 수정은 owner만. DB는 최대 한 명을 제한하며 반드시 한 명 존재하게 만드는 것은 별도 운영 책임 |

`identity` 권한이 위임되면 신원 관련 접근 범위가 달라질 수 있다. 신원 접근 권한과 admin 역할에 고정된 제재 제한을 동일한 개념으로 취급하지 않는다. 근거: [adminRoles.ts](../src/lib/adminRoles.ts), [adminAuth.ts](../src/lib/server/adminAuth.ts), [schema.sql](../supabase/schema.sql).

## 3. 정보 구조

학생 하단 탭은 **익명편지 `/letters` — 채팅 홈 `/` — 프로필 `/me`**의 세 개다. 탭은 이 세 루트 화면에서만 표시하며 대화방·편지 쓰기·설정 등에서는 뒤로가기를 제공한다.

| 영역 | 주요 화면 | 역할 |
|---|---|---|
| 진입 | `/install`, `/login`, `/onboarding` | 설치·인증·첫 설정 |
| 채팅 | `/`, `/chat/[id]` | 대화 목록, 매칭, 실제 대화. AI는 홈 위 창 |
| 편지 | `/letters`, `/letters/new`, `/letters/m/[id]`, `/letters/m/[id]/reply` | 우체통, 대상 검색/작성, 봉투 열기, 답장 |
| 보관 | `/letters/archive`, `/letters/f/[id]` | 받은/보낸 편지, 개인 폴더 |
| 프로필 | `/me`, `/me/achievements`, `/me/achievements/submit` | 소개·선호·매너 온도·업적·인증 신청 |
| 알림 | `/activity`, `/notices/[id]` | 새 채팅/편지, 전체 공지, 개인 공지 |
| 설정/지원 | `/settings`, `/settings/contact`, `/settings/[doc]` | 표시/알림/계정/편지 설정, 문의, 약관·개인정보·운영정책 |
| 운영 | `/admin` 이하 | 신고·사용자·대화·문의·공지·뱃지·설정·감사·운영진 |

`/chat`, `/notices`, `/letters/[id]`는 과거 주소 호환 경로다. 신규 탐색에는 위 현행 주소를 사용한다. `/dev/*`는 개발 미리보기로 제품 메뉴와 분리한다.

## 4. 요구사항 표기

우선순위는 **Must**(핵심 기능/안전/출시 조건), **Should**(제품 품질/운영 효율), **Could**(후속 검증 후보)로 적는다. 이는 종합 검토의 보안·개선 심각도 P1/P2와 별개다.

구현 상태는 **구현**(코드 경로 존재), **조건부**(운영 설정·권한·환경 필요), **보완**(기능은 있으나 알려진 공백), **제안**(새 요구사항, 구현 완료 아님)이다. 수용 기준은 앞으로 확인해야 할 결과를 포함한다.

### 5.2 랜덤 매칭·대화·동의

| FR-09 | 메시지·공감·인용 답장·삭제·재전송을 제공한다 | Must · 구현 | 전송 UUID로 중복 방지. 낙관적 표시와 서버 확정 구분, 규칙 위반/오류를 전달하고 재연결 시 빠진 메시지 복구 |
| FR-10 | 만료 구간에 양쪽 연장 동의와 단계별 정보 공개를 제공한다 | Must · 구현 | 한쪽 거절이면 종료. 입력형 힌트 검증. 동의 전 공개 금지. 최종 단계 이후 쌍방 동의로 고정 |

## 6. 핵심 정책과 현재 기본값

아래는 **현행 코드/새 DB의 SQL 기본값**이다. 오래된 README·주석·보안 문서와 다른 값이 있으며 운영자는 설정을 바꿀 수 있다. PWA가 표시하는 실제 값은 서버 설정과 상태를 우선한다.

| 정책 | 현재 기준 | 제품상 의미 |
|---|---|---|
| 첫 대화/일반 연장 | 5분 / 10분 | README 첫 줄의 10분을 현재 기본 시작 시간으로 복제하지 않음 |
| 입장 유예/연장 구간 | 60초 / 만료 90초 전 | 쌍방 입장과 투표 가능 시점을 구분 |
| 연장 제한 | max_rounds=0이면 상한 없음 | 실제 고정 단계·운영 상한 판단이 먼저 적용 |
| 공개 순서 | 학년 → 공통 질문 1 → 디플로마 → 공통 질문 2 → 동아리 | 과거 성씨 공개 주석은 현행 순서가 아님. 입력형 정보는 사용자가 정함 |
| 대화 고정 | 위 5단계를 지난 다음 연장 구간에서 양쪽 동의 | 시간 제한·pause 없음, 일반 동시 대화 개수 제외 |
| 동시 일반 대화 | 기본 5개 | 고정 대화 제외. 운영 설정 범위 1~20 |
| 재매칭 | 기본 cooldown 7일 + 재매칭 선호 | 서로의 차단/선호와 함께 판단 |
| 채팅/편지 본문 | 채팅 최대 500자, 편지 최대 1,000자 | 서버 검증이 최종 기준 |
| 편지 검색/추천 | 최소 2글자·최대 10명 / 최대 5명 | 동명이인 구분. 추천 제외 선호 제공 |
| 편지 기능 잠금 | 기본 활성, 인증·온보딩 학생 100명 기준 | 단순 총 auth 계정 수가 아님 |
| 새 편지 예산 | 토큰 용량 50, 하루 약 50통 분량 보충 | 자정마다 50회로 초기화되는 일일 카운터가 아님 |
| 무응답 연속 전송 | 한쪽에서 최대 3통 | 새 thread 예산과 이어 쓰기 예산 구분 |
| 편지 폴더 | 이름 최대 20자, 30개 | 동시 생성 상한 보완 필요 |
| 뱃지 신청 | 대기 최대 3건, 최근 24시간 최대 5건, 사진 1~3장 | 취소가 항상 모든 이용 예산을 되돌리는 것은 아님 |
| 사진 업로드 | 장당 5MiB, 저장 중 12장, 최근 24시간 15장 | 비공개 버킷. 미제출 사진은 1시간 후 정리 대상 |
| AI | 기본 꺼짐. 세션 기본 10분·30턴, 개인/전체 예산은 설정 | 운영 활성화·안내·모델/바인딩·처리 예산 확인 필요 |
| OTP | UI는 6~8자리 허용, 운영 문서 목표 8자리·10분 | 실제 길이/만료는 Auth 프로젝트 설정 확인 필요 |
| 평가 반영 | 생성 6시간 이후 평가를 예약 작업으로 묶어 반영 | 같은 상대의 7일 내 반복 평가를 제한해 추론 완화 |

차단·신고는 채팅과 편지에 공유된다. 차단 여부가 이름 검색/발신 성공 여부의 차이로 익명 발신자에게 연결되지 않도록 **발송 접수와 실제 수신 전달을 구분**한다. 학생에게 전달 여부 내부 플래그를 공개하지 않는다. 따라서 ‘보냈어요’를 ‘수신자가 받았어요/읽었어요’로 바꾸지 않는다.

정책 안내는 위 처리와 실제 구현을 맞춰야 한다(R05). 학생에게 ‘완전히 익명’, ‘24시간에 정확히 삭제’, ‘사진은 즉시 완전히 삭제’처럼 코드·운영이 보증하지 못하는 표현을 쓰지 않는다.

## 9. 성공 지표와 계측 제안

현재 운영 기준선과 목표값은 미확인이다. 아래는 신규 계측 설계이며 이미 있는 분석 이벤트로 간주하지 않는다.

**핵심 지표 후보:** 주간 유효 대화를 경험한 학생 수. 유효 대화는 ‘서로 최소 한 번씩 말한 랜덤채팅’ 또는 ‘최초 편지에 상대 답장이 발생한 대화’로 정의한다. 단순 보낸 편지 수·AI 메시지 수는 이 지표에 포함하지 않는다.

| 지표 | 정의 | 함께 볼 보호 지표 |
|---|---|---|
| 인증/온보딩 전환 | 인증 성공 학생 중 일정 관찰 기간 내 온보딩 완료 비율 | OTP 실패·재전송·공용 IP 제한, 이름 설정 실패 |
| 첫 유효 대화 전환 | 신규 온보딩 완료 학생 중 제안 관찰창 7일 내 유효 대화 경험 비율 | 첫 주 신고/차단, 매칭 실패, 반복 재시도 |
| 매칭 도달 시간 | 찾기 시작→방 배정의 p50/p95, 중도 취소는 별도 | 서비스 운영 시간·동시 접속·선호·상한 조건 |
| 쌍방 채팅 비율 | 시작된 대화 중 양쪽 최소 한 메시지를 보낸 비율 | no_show·빠른 종료·규칙 거절 |
| 쌍방 연장 비율 | 투표 가능 구간에 도달한 대화 중 양쪽 동의 비율 | 압박 없는 거절, 신고/차단율 |
| 편지 답장 비율 | 실제 전달된 최초 편지 중 제안 관찰창 7일 내 답장 비율 | 수신 거부·미열람·무응답 전송, 차단 추론 없음 |
| 재방문 | 활성 코호트의 D7/W1 재방문율 | 불필요한 알림, 만족도와 안전 지표 |
| 안전 대응 | 신고 접수→최초 검토→처리 시간 p50/p95, 미처리 수/최고 대기 시간 | 오탐/이의 제기·재신고·권한 오남용 |
| 운영 건강 | 전송 실패율, 부팅 실패율, AI pending 연령, 사진 삭제 지연, cron 실패율 | 재시도 비용·DB 호출/메모리·중복 사용자 턴 |

계측 후보 이벤트는 `onboarding_completed`, `seek_started/stopped`, `match_assigned`, `room_started/closed`, `extension_resolved`, `letter_sent/opened/replied`, `report_created/resolved`, `inquiry_answered`다. **현재 이벤트 API가 있다는 뜻은 아니다.**

이벤트 payload에 글 원문·이름·학번·이메일·사진·발신자 추론 단서를 넣지 않는다. 계정별 재방문 측정은 가명 id라도 개인정보 처리 범위와 보관 정책을 먼저 정한다. 대화 원문 purge 이후 지표를 산출하려면 필요한 최소 집계값을 정리 전에 만드는 설계가 필요하다. 상세 편지 전달 여부는 서버 집계에서만 사용하고 학생 화면이나 공개 분석에서 드러내지 않는다. 목표치는 기준선 측정과 운영 인력 합의 후 설정한다.

## 10. 단계별 제품 개선과 출시 기준

새 MVP를 만드는 계획이 아니라 이미 구현된 서비스의 요구사항을 정렬하는 계획이다. 일정·담당자·출시일은 합의 전이다.

| 단계 | 결과물 | 연결 요구사항/검토 |
|---|---|---|
| A. 사용 신뢰/안전 | 부팅 재시도, 글 초안, 나가기 성공/실패, 사진 심사, 처리 안내, 서버 검토 지속 | FR-05/15/24/26/27, R01~R05/R07 |
| B. 권한·운영 일관성 | Auth 재확인, 통계 최소 권한, 점검 차단, AI 중복 방지, 채널 종료 경계, Push 처리 상태 | FR-04/13/28/30/32/36, R06/R08/R09/R24~R26/R29 |
| C. 읽기 품질·확장 | 접근성·PWA 갱신, 긴 대화 페이지, 요청 budget, 폴더 경합, FK 정리, export 일관성 | NFR-04~08, R13~R23/R27/R28 |
| D. 제품 가설 검증 | 활성화/유효 대화 기준선, 설치 전 소개, 연출 속도/건너뛰기 평가 | 지표 계측 설계 및 사용자 테스트 |

**출시 확인 항목**

- 신규 학생·재방문·비밀번호 분실·온보딩 미완료 경로가 실제 기기에서 완결된다.
- 채팅 쌍방 입장/시간 정지/동의/고정/종료와 편지 수신 거부가 의도한 정책을 따른다.
- 신고·차단·심사·문의 결과가 학생에게 전달되고 필요한 감사 기록이 남는다.
- 타인·제재·권한 없는 운영자 요청을 서버/DB에서 차단한다. 복수 DB 연결 경쟁 조건을 검증한다.
- 정책 안내와 데이터 보존·AI·사진·export 동작이 일치한다.
- 타입 검사·관련 회귀 테스트·빌드·production 설정의 브라우저 검증을 완료한다. 이전 검토의 테스트 통과를 이번 출시 확인으로 대체하지 않는다.
- 운영 Auth·CSP·Storage·Realtime·DB cron·Worker cron·백업이 대상 배포에서 확인된다.
