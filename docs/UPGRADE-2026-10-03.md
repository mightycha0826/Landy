# Landy 검토 후 업그레이드 — 2026-10-03

[종합 검토](./PROJECT-REVIEW-2026-10-03.md)의 R01–R29를 기준으로 앱·서버·DB·접근성을 개선했다. 아래의 ‘반영’은 10월 3일 작업 당시 저장소 코드에 반영했다는 뜻이다. 당시에는 운영 Supabase 마이그레이션과 Cloudflare 배포를 수행하지 않았다.

**10월 4일 운영 DB 반영:** 운영 로그인 장애를 조사해 누락된 10월 2일 보안 변경과 10월 3일 업그레이드 마이그레이션을 Supabase `LOVE`에 적용했다. 세션 발급·검증·폐기 및 접근 권한을 실제 DB에서 검증했다. 적용 이력과 확인 범위는 [운영 DB 반영 기록](./DB-MIGRATION-2026-10-04.md)에 정리했다.

## 사용자가 보게 되는 변화

- 계정 정보를 못 읽으면 오류와 재시도 버튼을 제공한다. 재시도와 계정 변경에 늦은 응답이 끼어들지 않게 한다.
- 편지 본문·서식·서명과 프로필 수정 내용을 기기에 복원한다. 같은 수신자를 다시 선택하면 해당 초안이 나타난다. 24시간이 지나면 읽지 않으며, 만료된 기기 데이터는 다음 접근 때 제거한다. 보내기·버리기·로그아웃·계정 전환 시에도 제거한다.
- 대화 나가기 실패 시 확인 화면과 대화를 유지한다. 대표 뱃지 변경은 앞선 저장이 끝난 뒤 가능하다.
- 고정 채팅은 최신 200개로 시작하고 이전 대화를 200개씩 더 읽는다. 메시지를 묶어 병합할 때 정렬은 한 번 수행한다.
- 테마에서 흰 글자가 올라가는 면과 밝고 어두운 종이의 글자색을 조정했다. 신고 사유·서식 토글의 선택 상태, 편집기 키보드 이동, 사진 확대 창의 포커스를 보완했다. 브라우저 확대와 기본 메뉴를 허용한다.
- `/legal/terms`, `/legal/privacy`, `/legal/policy`를 설치·로그인 없이 읽을 수 있다. 설치 화면에 앱 소개와 정책 링크를 제공한다.
- 서비스워커 캐시 버전은 빌드에서 생성한다. 새 버전은 사용자가 업데이트 버튼을 눌러 적용한다.

## DB와 배포 순서

새 파일: [`20261004020721_project_review_upgrade.sql`](../supabase/migrations/20261004020721_project_review_upgrade.sql). Supabase CLI의 `migration new`로 만들고 snapshot을 함께 갱신했다. 기존 설치에는 누락된 이전 마이그레이션을 먼저 적용하고 이 파일을 적용한다. 기존 DB에 `schema.sql` 전체를 덮어쓰는 방식은 사용하지 않는다.

1. 운영과 같은 staging DB에서 마이그레이션과 역할별 접근을 확인한다. API는 새 RPC에 의존하므로 DB를 먼저 적용한다.
2. Supabase Auth의 비밀번호 재인증 설정, `auth.sessions` 사용 가능 여부와 운영 ACL을 확인한다.
3. Cloudflare에 같은 Supabase 프로젝트의 서버 키·공개 설정·VAPID·AI 바인딩을 확인한 뒤 Worker를 배포한다. cron은 매분, 사진 정리는 그중 15분마다 실행한다.
4. 운영자 재로그인 후 사진 열람, CSV 두 조각, 세션 폐기, AI 중복 요청, 학생 호출 없는 검토, 실패 푸시 재시도를 실제 환경에서 확인한다.

새 private 표에는 학생 직접 접근 권한을 주지 않는다. 응답 캐시는 15분 후 읽지 않으며 정기 작업이 본문을 정리한다. outbox에는 알림 본문을 저장하지 않고 참조·발송 상태를 보관한다. 기존 운영자 CSV 다운로드 파일은 앱이 회수하거나 지울 수 없다.

실제 비밀값을 읽지 않도록 `LANDY_ENV_DIR`에 빈 임시 디렉터리를 지정했다. 브라우저/Worker 테스트의 Wrangler registry도 임시 경로로 분리했다. 검증의 최신 결과는 아래에 기록한다.

- 타입 검사: `npm run check` — 오류 0, 경고 0.
- 프로덕션 빌드: `npm run build` — 통과.
- Cloudflare Worker: 임시 설정의 `wrangler deploy --dry-run` — 번들 생성 통과, 업로드·배포 없음.
- 단위·서버·예약 작업·보안: 최신 코드의 `npm test` — 통과. 일반 검사 325개와 보안 회귀 probe를 포함한다.
- DB: PGlite 1,126개 통과. 새 마이그레이션과 snapshot 함수 일치, 검토 실패의 예산 보존도 포함.
- 브라우저: 24개 스위트·915개 검사 모두 통과. 설치 전 정책 열람, 사진 실표시·확대·포커스, 초안 버리기·새로고침 복원·전송 후 삭제, CSV 작업을 포함한다. 폭 280~520px의 10개 크기에서 기존 화면들의 줄바꿈·잘림·넘침 검사도 통과했다.
- 브라우저 실행기: 스위트마다 개발 서버를 정리하고 실행 시간 제한을 둔다. 폭 검사는 별도 로그인 검사의 통과를 전제로 가짜 인증 세션을 고정하며, 폭 두 개마다 테스트 브라우저를 재시작해 Chromium 자원 부족을 피한다. 로그인 전 화면도 각 폭에서 따로 검사한다. 스크린샷은 OS 임시 폴더에 저장한다.
- 실제 PostgreSQL: CI에 전용 `landy_review_test` DB와 다중 프로세스 검사 추가. 현재 로컬에서는 미실행.

## 후속 Ponytail 리팩토링

로컬 설정의 `ponytail` 마켓플레이스와 캐시의 플러그인 메타데이터(v4.10.1)를 확인했다. 해당 저장소의 `ponytail`, `ponytail-audit`, `ponytail-review` 스킬을 직접 읽고 기본 `full` 기준을 적용했다. 코드 삭제·기존 구현 재사용·표준 기능을 우선하고, 데이터 손실 방지와 권한 검사는 유지했다.

- 편지함과 폴더: 각각 첫 페이지/더보기의 응답 적용, 오류 처리, 재시도와 요청 수명 처리를 통합했다. 기존 공개 함수와 계정·화면 전환 후 늦은 응답 차단은 유지한다.
- 채팅: 봇 화면에서도 사용하는 `Array.findLast`로 내 마지막 메시지와 낭독할 상대 메시지를 검색한다. 읽음 표시와 최초 기록의 낭독 기준선은 유지한다.
- AI 요청: 성공·실패 완료가 같은 요청 ID와 승인 lease를 전달하도록 지역 함수를 공유한다. 캐시·거절·lease 만료·모델 실패·완료 저장 실패를 재현하는 검사 하나를 기존 서버 검사에 추가했다.
- 첫 작업에서는 구현 코드 4개 파일에서 순수하게 27줄을 줄였고, 새 의존성과 새 구현 파일은 추가하지 않았다. Realtime 전송 추상화는 실제 전송과 테스트 전송이 모두 사용하므로 유지한다.
- 검증: `npm test` 통과(일반 검사 326개, 보안 회귀 probe, PGlite 1,126개). 브라우저 `react`, `a11y`, `letters`, `bot`, `back` 5개 스위트의 검사 381개 통과. 공감 검사의 첫 실행은 초기 화면 대기 시간 초과로 실패했으나 단독 재실행에서 26개 모두 통과했다. 최종 `npm run check`는 오류 0·경고 0, `npm run build`도 통과했다.

기존 마케팅 생성물의 Git 제외 규칙은 유지한다. 이번 리팩토링으로 DB 마이그레이션이나 운영 배포를 수행하지 않았다.

### 설정 화면과 운영자 신고 목록으로 범위 확장

첫 작업의 범위가 좁다는 피드백을 반영해 큰 화면의 책임과 반복되는 사용자 동작을 추가로 정리했다. 실제로 함께 쓰이는 동작만 분리했고, 새 의존성은 추가하지 않았다.

- `PasswordSettings.svelte`: 현재 비밀번호 확인·메일 코드·새 비밀번호 저장의 상태와 입력을 소유한다. 네 인증 요청의 성공·오류 처리를 공유하고, 취소 시 입력을 지운다. 취소 후 늦은 응답, 화면 이탈 또는 계정 전환 후 응답이 인증 단계를 다시 열거나 새 입력을 지우지 않도록 요청 수명을 검사한다. 서버의 재인증 정책과 기존 Auth API는 유지한다.
- `ProfileSwitch.svelte`: 재매칭·편지 받기·추천 노출 세 옵션의 중복 저장 흐름을 통합했다. 저장 전에는 기존 값을 표시하고, 실패하면 다시 시도할 수 있다. 저장 중 중복 클릭과 계정/화면 전환 후 알림을 막고, 편지 받기를 끄면 추천 옵션을 비활성화한다.
- `ReportList.svelte`: 운영자 채팅·편지 신고의 상태 탭, 빈 목록, 표와 모바일 열 표시를 공유한다. 종류별 열 순서와 상세 경로는 유지하고 props 타입으로 목록 종류와 데이터의 조합을 제한한다. 조회 권한·실명 열람·제재 처리는 기존 서버 코드에 남긴다.
- 설정 페이지에서 250줄가량의 인증·옵션 코드와 마크업을 옮기거나 제거했다. 파일 크기 감소 자체보다 비밀번호, 옵션 저장, 푸시 설정을 독립적으로 수정할 수 있게 하는 것이 목적이다. 모든 큰 화면이나 모든 비동기 요청을 이번 작업으로 정리한 것은 아니다.
- 브라우저 회귀 검사에 옵션 저장 실패·재시도, 추천 의존 조건, 인증 취소 중 응답 지연, 비밀번호 저장을 추가했다. 신고 목록은 종류별 상세 이동, 데스크톱/모바일 열 표시, 필터와 빈 상태를 검사한다.
- 확장 작업의 최종 검증: `back` 110개·`login` 20개·`audit` 138개, 총 268개 브라우저 검사 통과. `npm run test:unit`의 일반 검사 326개와 보안 회귀 probe 통과. `npm run check` 오류 0·경고 0, `npm run build` 통과. DB 변경은 없으며 PGlite는 첫 작업의 1,126개 통과 기록을 유지한다. 마케팅 생성물 23개가 계속 Git에서 제외되는 것도 다시 확인했다.

## 후속 앱 최적화

리팩토링은 기존 동작을 유지하며 코드 구조를 정리하는 작업이다. 최적화는 다운로드·요청·계산 등의 비용을 줄이는 작업이다. 이번에는 다운로드·중복 조회·정렬 비용을 줄이고, 검증에서 발견한 느린 화면 이동 문제도 고쳤다.

- 새 편지의 받는 사람 선택: `EnvelopeCompose`와 Tiptap을 받는 사람을 선택한 뒤에 가져온다. [Svelte의 공식 지연 로딩 방식](https://svelte.dev/docs/svelte/await)을 사용했다. 준비 중에는 상태를 표시하고 돌아갈 수 있으며, 다운로드 실패 시 안내와 새로 불러오기 버튼을 표시한다. 답장의 기존 로딩 방식과 편지 초안·서식·전송 기능은 유지한다.
- 채팅 기록: `MessageLedger.merge`는 메시지 순서가 바뀔 때만 묶음을 정렬한다. 비어 있는 동기화, 같은 ID의 중복 응답, 순서대로 추가된 새 메시지는 전체 정렬을 생략한다. 과거 메시지와 낙관적 메시지의 서버 ID 확정은 정렬이 필요하므로 유지한다. 10,000개 기록에서 빈 동기화 100회와 순차 추가의 정렬 호출이 0회임을 실제 상태 모듈로 검사했다.
- 안 읽은 편지 수: 같은 계정의 진행 중 조회를 공유한다. 동시 호출 5회를 서버 요청 1회로 처리하는 검사를 추가했다. 읽기·삭제 직후에는 진행 중인 옛 응답을 무시하고 새 상태를 한 번 더 읽는다. 계정 전환 시에는 이전 요청 공유와 응답 적용을 중단한다. 실패 후 재시도도 유지한다. Supabase RPC·권한·DB 스키마는 바꾸지 않았다.
- 느린 화면 이동: 우체통에서 편지를 꺼낼 때 전달하는 위치 정보의 2초 만료가 느린 코드 다운로드보다 먼저 끝나는 문제를 브라우저 검사에서 발견했다. 이동을 시작하면 완료 또는 실패까지 정보를 유지하고, 완료 후 정리한다. 아직 시작하지 않은 이동의 정보는 기존대로 2초 후 만료한다. 편지 화면 코드를 2.6초 지연하는 회귀 검사와 실제 상태 모듈의 수명 검사를 추가했다.

### 빌드 비교

같은 로컬 환경의 프로덕션 빌드 manifest에서 `/letters/new`와 공통 레이아웃의 정적 JavaScript 의존 파일을 중복 없이 합산했다. 현재 생성된 노드 0·2·3·15의 `imports`를 재귀적으로 순회한 값이며, 동적 import·CSS·폰트·앱 시작 entry는 제외한다. gzip은 각 파일에 Node `gzipSync`를 적용한 합이다.

| 비교 항목 | 변경 전 | 변경 후 | 감소 |
|---|---:|---:|---:|
| 정적 JS 의존 파일 합 | 792,554 bytes | 439,435 bytes | 44.6% |
| 같은 파일의 gzip 합 | 255,387 bytes | 147,602 bytes | 42.2% |

333,655 bytes의 편집기 JS 청크는 받는 사람 선택 이후로 옮겨졌다. 앱 전체 코드가 삭제된 것이 아니며, 처음 편지를 실제로 쓸 때는 해당 코드를 내려받아야 한다. 브라우저 캐시와 서버 압축에 따라 실제 네트워크 전송량은 다르다. 체감 속도의 개선 비율이나 운영 DB 비용 절감률은 이번 로컬 검사로 단정하지 않는다. 실제 학교망·기기에서의 LCP/INP, 메시지 DOM 가상화, 고정 채팅 전체 공감 조회 범위와 운영 DB 실행 계획은 추가 측정 대상이다.

### 최적화 검증 기록

- `npm run test:unit`: 일반 검사 338개와 보안 회귀 probe 통과. 실제 채팅 상태 모듈 118개, 편지 상태 모듈 49개 검사를 포함한다.
- `npm run check`: 오류 0·경고 0. `npm run build`: 통과. 새 패키지·DB 마이그레이션·운영 배포는 없다.
- 브라우저 공감 검사 `react`: 26개 통과. 편집기 지연 로딩·취소·실패 및 실제 작성·서식·초안·전송·설정·키보드·공유 흐름은 편지 검사에서 확인했다.
- 편지 전체 실행의 최신 결과는 206개 통과·지연 주입 요청 계수 1개 실패였다. 처음에는 요청이 정확히 1개라고 가정했으나 Vite가 같은 컴포넌트의 JS와 CSS를 각각 요청했다. 적어도 한 요청이 실제로 지연됐는지를 검사하도록 계수를 고친 뒤, 저장된 같은 검사 코드의 앞부분을 별도 개발 서버에서 재실행해 27개 전부 통과했다. 실제 지연 요청 2개와 우체통 위치 유지도 확인했다. 계수 수정 뒤 전체 스위트를 다시 실행하지는 않았다.
