# 운영진방 계정 삭제 — 2026-10-04

학생의 계정 삭제 요청을 `/admin/inquiries`에서 실제로 처리한다. 삭제 실행은 `admin` 역할만 가능하고 문의 권한만 있는 운영자·개발자는 요청을 관리자에게 전달한다.

## 운영 방법

1. 문의 목록의 **계정 삭제 요청**에서 요청자와 처리 범위를 확인한다. 삭제 후 학생이 앱의 답변을 볼 수 없으므로 필요한 안내는 먼저 전달한다. 요청을 거절하거나 추가 확인이 필요하면 기존 답변 기능을 사용한다. 답변한 요청에서는 삭제를 시작할 수 없다.
2. **요청한 계정 삭제**를 펼쳐 대상 이름표·계정 ID·문의 번호를 확인한다.
3. 처리 사유와 요청 확인 내용을 5~1000자로 입력하고 **삭제 {문의 번호}**를 입력한다. 삭제 범위 확인 체크 후 최종 확인창에서 실행한다.
4. 완료 여부는 **삭제 처리 내역**과 활동 기록에서 확인한다. 문의 자체는 계정 삭제에 따라 함께 삭제된다. 실패하면 중단 단계와 재시도 폼이 표시된다. 응답 없이 처리가 중단됐으면 10분의 실행 임대가 만료된 후 새로고침해 재시도한다.

자기 계정과 운영진 명단에 있는 계정은 이 경로에서 삭제하지 않는다. 일반 문의·다른 학생의 요청 번호·확인 문구 오류·다른 운영자의 실행 중복은 서버와 DB에서 차단한다.

## 삭제 범위

인증 계정·프로필·업적·문의·알림/개인 설정 등 계정에 연결된 FK 데이터를 삭제한다. 보낸 편지와 받은 편지는 상대방의 보관함에서도 삭제되므로 실행 전에 이를 확인한다. 진행 중인 채팅은 닫고 학생이 소유한 Storage 파일과 증빙 사진을 Storage API로 삭제한 뒤 Auth Admin API로 인증 계정을 영구 삭제한다.

대화 기록과 신고 증거는 기존 보관 정책을 따르고, 학교 명렬표·운영 활동 기록·최소 삭제 처리 원장은 남긴다. 백업·이미 내려받은 CSV·상대의 화면 캡처·기기에 남은 로컬 초안과 캐시는 이 기능이 원격으로 지우지 않는다. 학교 명렬표가 남으므로 같은 학교 이메일의 새 가입을 영구 금지하는 기능도 아니다.

Supabase의 기존 JWT 서명은 만료 전까지 유효할 수 있다. 준비 단계에서 프로필을 이용 제한 상태로 바꾸고 대기를 중지하며 채팅을 닫는다. Auth API로 로그인 제한 후 영구 삭제하며, 프로필·방 참여 행 등이 삭제돼 해당 계정의 앱 데이터 접근이 거부된다. 모든 외부 JWT 소비 시스템의 토큰을 즉시 무효화한다고 표시하지 않는다. [공식 사용자 삭제 문서](https://supabase.com/docs/guides/auth/managing-user-data).

## 실패와 재시도

Auth·Storage와 DB는 하나의 트랜잭션으로 묶을 수 없다. 삭제 전에 비공개 원장과 감사 기록을 남기고 DB에서 대상 계정을 다시 검증한다. 일부 파일이 삭제된 뒤 실패할 수 있으므로 제한을 자동으로 풀거나 이전 상태로 되돌렸다고 표시하지 않는다.

`auth_lock` / `storage` / `auth` / `record` 중단 단계를 기록하고 화면에는 한국어로 설명한다. 인증 계정 삭제 후 완료 기록만 실패한 경우 재시도는 Auth 삭제를 반복하지 않고 실제 DB·파일 상태를 확인해 완료 기록을 복구한다. 실패 응답에도 화면을 다시 조회한다. 원장에 임대 토큰을 넣어 중복 처리를 막고, 만료된 실행은 새 임대로 다시 확인한다.

비공개 `private.account_deletions`는 RLS를 켜고 학생·익명 역할의 직접 접근을 차단했다. 새 RPC 3개는 `service_role`만 호출할 수 있으며 함수 내부에서도 현재 관리자 역할을 확인한다. 서비스 키는 서버 전용 모듈에서만 사용한다. [공식 Auth 삭제 API](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser).
